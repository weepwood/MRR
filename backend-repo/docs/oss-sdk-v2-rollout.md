# OSS SDK v2 发布验收与回滚

本次只更换 Java S3 客户端。生产仍使用现有 Windows Server、Nginx 和受管发布包；OSS 凭据、endpoint、bucket、region 与 path-style 配置保持原值。不要把配置值、对象键或签名 URL 写进测试日志、Issue 或截图。

## 发布前

1. 保留当前受管理发布包、`previous` 指针、配置备份和数据库备份。确认当前 manifest 允许应用回滚；本变更没有 Flyway 迁移。
2. 在与生产相同的 S3 兼容存储版本及网络路径上准备**虚构数据**的专用测试前缀。确认有上传、读取、列目录、签名和删除权限。
3. 运行 `mvnw.cmd -B -ntp test`、`mvnw.cmd -B -ntp verify`；检查依赖树不含 `com.amazonaws:aws-java-sdk-s3`。

## 目标环境验收

在维护窗口内，通过系统现有后端接口和受控权限执行：

1. 上传小型虚构影像，核对源 MD5 元数据、服务端 Content-MD5 校验和再次读取的字节一致性。
2. 对同一测试前缀列目录，检查目录优先排序、分页游标和最大 500 条边界；生成短期签名地址，确认过期、受管前缀限制及实际可读取。
3. 查询不存在对象应返回“未找到”；用测试凭据分别模拟权限拒绝与连接超时，确认脱敏错误、审计及重试边界。
4. 删除该虚构对象后确认不存在。验证受保护影像的后端内容网关、Windows 服务启动与停止，以及已关闭的响应流。

验收必须记录通过/失败结论和发布包版本，不记录对象键、凭据、真实患者信息、内网 endpoint 或签名 URL。单元测试和本地模拟 HTTP 端点不能代替以上验收。

## 回滚

若上述任一步失败，停止新包的 OSS 写入操作并进入维护模式；确认失败上传没有留下待处理的虚构对象。先核对部署包 manifest 与当前 `release-baseline.json`。当前 `applicationRollback.allowed=false`，不得直接执行 `mrrctl.ps1 rollback previous`，也不得用 `-Force` 绕过兼容性限制。应在当前主线保留数据库迁移、令牌撤销与安全修复，仅撤销本次 OSS SDK 迁移，构建新的受管理发布包；按 `deploy/windows/README.md` 验证清单、安装并复测读取、签名、分页和后端健康检查。只有后续基线明确允许应用回滚且现场完成兼容演练时，才使用受管理回滚命令。此恢复过程不会改变 OSS 已写入的对象，应根据审计记录逐项核对并处理。
