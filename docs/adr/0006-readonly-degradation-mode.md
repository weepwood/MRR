# ADR-0006：只读降级模式（主动维护 + 自动降级）

## 背景

医院内网系统中，维护窗口、数据库故障或后端异常时，若继续接受写操作可能导致数据不一致或半完成事务。需要一种明确的"只读"状态：维护期间主动拒绝写入，故障时自动降级保护数据，同时读路径保持可用以满足调阅需求。此前缺乏统一的只读语义，各接口自行判断，易出现不一致。

约束：

- 只读是可用性边界决策，不得绕过权限或审计；
- 状态必须持久化，重启后仍生效（与配置一致）；
- 自动降级与主动维护必须能共同生效，且可恢复；
- 不得因只读模式而暴露敏感信息或放宽权限。

## 决策

采用 **主动维护只读 + 自动只读降级** 双机制，状态持久化到系统设置：

- 管理员可在系统设置主动开启"维护只读模式"，持久化并在重启后保持；
- 后端在检测到关键依赖不可用（如数据库/存储异常）时触发**自动只读降级**；
- 两种模式共同生效：任一为真即进入只读；
- 只读期间写类接口（编辑、下载导出、管理操作等）被拦截并返回明确状态；
- 只读状态在运维诊断中心可见，并提供"最近运维操作"与快捷入口。

## 必须保持的不变量

- 只读模式下写操作必须被拒绝，且拒绝原因对运维可见；
- 只读状态不替代、不放宽任何权限或审计；
- 只读状态持久化，重启后不丢失；
- 自动降级可恢复，依赖恢复后自动/手动退出只读。

## 方案边界

### 包含

- 主动维护只读开关与持久化；
- 自动只读降级的触发与恢复；
- 写接口的统一只读拦截；
- 运维诊断中心对只读状态的展示。

### 不包含

- 只读模式下的数据修复写入（修复需退出只读并在审计下进行）；
- 读写分离/多副本（架构仍为单 PG，不做集群）。

## 替代方案

### 方案 A：故障时不降级，直接返回 5xx

- 优点：实现简单。
- 缺点：调阅（读）也不可用，且半完成写风险高。
- 未采用原因：违背"读路径保持可用"与数据保护目标。

### 方案 B：各写接口自行判断依赖

- 优点：局部可控。
- 缺点：语义不一致，易出现遗漏与竞态。
- 未采用原因：缺乏统一边界，难以审计与运维。

## 影响

### 正面影响

- 维护与故障场景数据安全性提升，读路径不中断；
- 状态统一、可观测、可恢复。

### 负面影响与技术债

- 自动降级阈值与恢复条件需调优，避免抖动；
- 只读拦截需覆盖所有写入口，存在遗漏风险，依赖测试。

### 安全、隐私与审计

- 只读不放松权限；审计照常；
- 维护模式本身不暴露额外敏感信息。

### 数据库、性能与容量

- 仅读取系统设置中的只读状态，开销可忽略；
- 不引入新表（复用系统设置）。

### Chrome 86、Windows 与部署兼容性

- 前端需兼容只读态下的交互提示；Windows 部署无新依赖。

## 迁移方案

- 配置：只读状态写入 `mr_system_settings`，随系统设置迁移持久化；
- 代码：`ReadOnlyDegradationInterceptor` 及相关拦截/服务；
- 文档：运维诊断中心与部署文档补充只读模式说明。

## 回滚与前向修复

- 关闭只读开关或恢复依赖即退出只读；
- 无数据库结构变更，回滚仅需代码/配置；
- 若自动降级误触发，提供手动强制退出并记入运维操作。

## 验证

- 单元测试：`ReadOnlyDegradationInterceptorTest`、`DeploymentReadinessServiceTest`、`DeploymentReadinessStatusTest`；
- PostgreSQL 集成测试：只读态下写接口被拒、读接口可用；
- E2E 或手工流程：开启维护只读→写操作被拦→关闭后恢复；
- 生产或灰度验证：维护窗口实际演练只读模式。
