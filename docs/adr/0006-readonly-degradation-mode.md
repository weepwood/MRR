# ADR-0006：只读降级模式（主动维护 + 自动降级）

- 状态：Accepted
- 日期：2026-10-09（补录；实现随 v0.7.0 合入 `main`，迁移 `V20260723090000` 相关设置）
- 决策者：MRR Team
- 关联 Issue：#92
- 关联 PR：#200
- 替代 ADR：无

## 背景

医院内网系统中，维护窗口、数据库故障或后端异常时，若继续接受写操作可能导致数据不一致或半完成事务。需要一种明确的"只读"状态：维护期间主动拒绝写入，故障时自动降级保护数据，同时读路径保持可用以满足调阅需求。此前缺乏统一的只读语义，各接口自行判断，易出现不一致。

约束：

- 只读是可用性边界决策，不得绕过权限或审计；
- 管理员主动维护状态必须持久化，重启后仍生效；自动降级依据就绪检查快照重新计算；
- 自动降级与主动维护必须能共同生效，且可恢复；
- 不得因只读模式而暴露敏感信息或放宽权限。

## 决策

采用 **主动维护只读 + 自动只读降级** 双机制：主动维护状态持久化到系统设置，自动降级状态保存在就绪检查的内存快照中：

- 管理员可在系统设置主动开启"维护只读模式"，持久化并在重启后保持；
- 后端在启动、定时或运维手动刷新就绪检查时，若关键检查失败则触发**自动只读降级**；
- 两种模式共同生效：任一为真即进入只读；
- 只读期间的写类请求被拦截并返回明确状态；安全 HTTP 方法和明确列入白名单的只读 POST 请求仍由各自的权限与业务校验处理，GET 下载不会被此拦截器拦截；
- 只读状态在运维诊断中心可见，并提供"最近运维操作"与快捷入口。

## 必须保持的不变量

- 只读模式下写操作必须被拒绝，且拒绝原因对运维可见；
- 只读状态不替代、不放宽任何权限或审计；
- 主动维护状态持久化，重启后不丢失；自动状态在重启后重新检查，不复用旧快照；
- 自动降级可恢复，依赖恢复并完成下一次就绪检查后退出自动只读。

## 方案边界

### 包含

- 主动维护只读开关与持久化；
- 自动只读降级的触发与恢复；
- 写接口的统一只读拦截；
- 运维诊断中心对只读状态的展示。

### 不包含

- 只读模式下的数据修复写入（修复需退出只读并在审计下进行）；
- 读写分离/多副本（架构仍为单 PG，不做集群）。

## 替代方案

### 方案 A：故障时不降级，直接返回 5xx

- 优点：实现简单。
- 缺点：正常读路径也可能被统一拒绝，且后续写请求缺少明确的降级状态。
- 未采用原因：无法按就绪检查结果统一阻断新增写请求；依赖故障时不能保证所有读请求仍可成功。

### 方案 B：各写接口自行判断依赖

- 优点：局部可控。
- 缺点：语义不一致，易出现遗漏与竞态。
- 未采用原因：缺乏统一边界，难以审计与运维。

## 影响

### 正面影响

- 维护与故障场景的数据保护边界更明确；依赖仍可用时，读路径继续由自身权限与业务规则处理；
- 状态统一、可观测、可恢复。

### 负面影响与技术债

- 自动降级阈值与恢复条件需调优，避免抖动；
- 只读拦截需覆盖所有写入口，存在遗漏风险，依赖测试。

### 安全、隐私与审计

- 只读不放松权限；审计照常；
- 维护模式本身不暴露额外敏感信息。

### 数据库、性能与容量

- 仅读取系统设置中的只读状态，开销可忽略；
- 不引入新表（复用系统设置）。

### Chrome 86、Windows 与部署兼容性

- 前端需兼容只读态下的交互提示；Windows 部署无新依赖。

## 迁移方案

- 配置：主动维护状态写入 `mr_system_settings`；自动降级状态由内存中的就绪检查快照计算；
- 代码：`ReadOnlyDegradationInterceptor` 及相关拦截/服务；
- 文档：运维诊断中心与部署文档补充只读模式说明。

## 回滚与前向修复

- 关闭主动维护开关，或依赖恢复后刷新就绪检查，即退出相应只读状态；
- 无数据库结构变更，回滚仅需代码/配置；
- 自动降级误报应修正检查条件或恢复依赖后重新刷新快照，不绕过仍失败的关键检查。

## 验证

- 单元测试：`ReadOnlyDegradationInterceptorTest`、`DeploymentReadinessServiceTest`、`DeploymentReadinessStatusTest`；
- PostgreSQL 集成测试：只读态下写接口被拒、读接口可用；
- E2E 或手工流程：开启维护只读→写操作被拦→关闭后恢复；
- 生产或灰度验证：维护窗口实际演练只读模式。
