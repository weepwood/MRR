# ADR-0007：受控只读数据库浏览（表数据查看）

- 状态：Accepted（2026-11-19 落地实现）；2026-11-19 修订：功能总开关默认由「关闭」改为「开启」，见文末「修订记录」。正文与实施进展中的「默认关闭」表述为修订前状态，保留以维持决策历史。
- 日期：2026-11-19
- 决策者：待定（需求发起人、后端负责人、安全与审计评审）
- 关联 Issue：#617（受控只读数据库浏览：运维按表查看数据，默认关闭）
- 关联 PR：本 PR（受控只读数据库浏览）
- 替代 ADR：无

## 背景

### 需求

运维与数据治理需要「按表查看数据」，用于回答：某条病案为何查不到、导入后行数与字段是否落地、字典与配置表当前取值是什么。当前只能登录服务器使用 psql，缺少受控、可审计、按账号授权的自助入口。

原始诉求是「前端直接查询所有表」。该表述对应三种完全不同的实现形态，风险差异极大，需要一次明确决策：前端直连数据库、后端代执行任意 SQL、后端受控只读浏览。本 ADR 只采纳第三种。

### 已确认事实（基于当前代码与部署）

1. 部署边界为「浏览器 → Nginx → Spring Boot 单体 → PostgreSQL 16」，数据库不向浏览器暴露，也不存在独立只读账号体系（`ARCHITECTURE.md` §1、§7）。
2. 已有只读监控 `GET /api/v1/system/database/overview|slow-queries|tables`（`DatabaseMonitorController`，权限 `system:read`），前端已有 `src/api/modules/database-monitoring.ts`。它们只返回元数据与表空间统计，不返回数据行。
3. 审计事实表为 `app.access_log`，由 `LogInterceptor` 对所有非跳过请求写入 `request_uri`、`query_string`、`request_body`，并用 `SENSITIVE_PARAMETER_NAMES` 做字段级脱敏（含 `idcard`、`phone`、`token` 等）。
4. `app.mr_scan` 为三千万级表；`app.mr_patient`、`app.mr_auth_user`、`app.mr_system_settings` 分别含姓名、身份证、病案号、密码哈希、配置值等敏感列。
5. `AuthorizationInterceptor` 对 `@RequirePermissions` 的多个权限取 **AND**（`allMatch`），且 `session.isAdmin()` 在权限判定前直接放行。
6. 只读降级模式（ADR-0006）拦截非白名单写请求；GET 不在拦截范围内。
7. 前端关键流程必须兼容 Chrome 86（无 `:has()`、无 `dvh`、`color-mix()` 需回退或降级）。

### 推断与未知项

- 推断：真实使用频次低（月级、个位数使用者），因此不必为高并发优化，但必须为零误用设计。
- 未知：生产库空闲连接与 IO 余量是否足以承载独立只读连接池，需现场测量后确认。
- 未知：使用者的角色边界（运维 / 数据治理 / 业务管理员）需试点期统计后再收敛授权范围。

## 决策

采用「受控只读数据库浏览」：由后端维护服务端表白名单与列级策略，向前端提供结构描述与数据行查询接口，仅支持 SELECT、游标分页、单列排序与受限过滤；不支持任意 SQL、写操作、DDL、跨表 JOIN 与整表导出。

功能默认关闭，使用独立权限 `system:db:browse`，全部浏览行为（成功与拒绝）写入审计。

不采用前端直连数据库，也不采用「后端代执行任意 SQL」。两者都不是「实现成本更低」的选项，而是把数据库边界整体撤销。

## 必须保持的不变量

1. 浏览器在任何情况下都不得获得数据库凭据、连接串或直连端口。
2. 系统不存在接收任意 SQL 文本的入口；HTTP 参数只作为绑定值进入 SQL，绝不参与 SQL 结构拼接。
3. 可浏览表、可见列、可过滤列、可排序列只能来自服务端注册表；未登记对象一律不可见（fail closed），注册表为空时接口返回空列表而非全表。
4. 浏览链路只读：不写业务表、不建业务临时表、不触发业务副作用；查询在只读事务中执行并设置语句超时。
5. 每次浏览（成功或拒绝）都可追溯到操作者、表、过滤条件摘要、返回行数与结果状态。
6. 含个人敏感信息的列必须先在服务端脱敏再出网；前端拿不到原值。
7. 三千万级表不得执行 `count(*)`，不得生成 `OFFSET` 或全表扫描；首屏只允许沿主键索引倒序取一页（`scan` / `patient` 上限 50 行），继续翻页必须携带游标。
8. 功能开关关闭时接口一律返回「资源不存在」语义（`3007`），前端拿不到任何表清单或数据行，只显示「未开启」提示；菜单入口本身按权限显示，不能靠隐藏菜单充当访问控制。

## 方案边界

### 包含

- 新增权限 `system:db:browse` 与可分配授权入口；
- 服务端浏览注册表（表级、列级、脱敏、过滤、排序、是否强制过滤）；
- 三个只读端点：表清单、表结构、数据行；
- 独立只读数据源、语句超时与行数预算；
- 表级浏览审计；
- 运维中心下的前端页面（开关控制、默认隐藏）。

### 不包含

- 任意 SQL 编辑器、查询保存、执行计划展示、慢查询改写；
- `INSERT` / `UPDATE` / `DELETE` / `DDL` / `COPY` / `VACUUM`；
- 跨表 JOIN、聚合报表、CSV/Excel 导出、整表下载；
- 视图、物化视图、外部表、分区子表的自动展开；
- 面向普通业务用户开放，也不替代病案查询页与统计页；
- 修改 `mr_scan` 数据、修复数据质量问题（仍走数据治理流程）。

## 替代方案

### 方案 A：前端直连 PostgreSQL

- 优点：零后端开发，任意查询能力，工具生态成熟。
- 缺点：必须把库凭据下发到浏览器并开放 5432；权限、审计、脱敏全部失效；任何能打开页面的人都能读全库。
- 未采用原因：直接违反「权限必须后端执行」「不把生产凭据交给浏览器」两条硬约束，且不可回滚。

### 方案 B：后端代执行任意 SQL

- 优点：实现快，一个输入框即可满足所有临时查询。
- 缺点：等价于把数据库包装成 HTTP；注入、越权、全表扫描、DDL 与锁表无法约束；审计只能记录 SQL 文本，无法结构化。
- 未采用原因：ADR-0002 已确立「诊断不得成为任意 SQL 探测入口」，本方案与之直接冲突。

### 方案 D：psql / pgAdmin 只读账号（并行的补充路径）

- 优点：零开发，能力最完整，适合 DBA 与深度排障。
- 缺点：无法与系统账号绑定，无法统一审计到 `access_log`，账号分发靠人工。
- 处理方式：不作为本 ADR 的替代，而作为并行的第一条路径先行落地；受控浏览只服务「不便登服务器」的内网自助场景。

## 影响

### 正面影响

- 把目前只能靠登服务器完成的核对动作纳入系统账号与审计范围；
- 排障、导入核对、字典确认不再依赖个人环境；
- 表与列的可见范围可集中收敛，比「发一个库账号」更可控。

### 负面影响与技术债

- 新增一套「表结构元数据 → HTTP 契约」的映射，schema 演进时需要同步维护注册表，否则新列不可见（这是刻意选择：不可见优于误暴露）。
- 注册表与真实表结构可能漂移，需要启动自检或集成测试兜底。
- 增加一个长期存在的敏感数据出口，后续每次放开一张表都要重新评估。

### 安全、隐私与审计

- 单个误配（把敏感表加入白名单且脱敏策略写错）即可造成批量泄露，因此注册表必须有集成测试覆盖每个已登记列。
- `session.isAdmin()` 会绕过业务权限：管理员天然可访问本功能。这一点必须在授权评审中显式确认，不能假设新权限能限制管理员。
- 请求级审计已被 `LogInterceptor` 覆盖（含 `query_string`），但过滤条件摘要、返回行数与结果状态需要业务审计补充，否则「看了哪 50 行」不可追溯。
- 浏览结果属于敏感响应，必须 `no-store`，且不得进入前端持久化（localStorage / IndexedDB / 状态持久化）。

### 数据库、性能与容量

- 每条查询受 `statement_timeout`（建议 3s）、行数上限（建议 200）与过滤条件数上限（建议 5）约束；
- 深分页一律游标，不使用大 `OFFSET`；
- 总行数只允许读估算值（`pg_class.reltuples`，从未 ANALYZE 时退到 `n_live_tup`），禁止 `count(*)`；
- 使用独立只读连接池（建议 `maximumPoolSize=2`），避免挤占业务 Hikari 连接；
- 三千万级表（`mr_scan`）允许不带过滤条件打开首屏，前提是排序键为主键且翻页只走游标，
  单页上限收紧到 50，单条语句 3s 超时；**仅当排序键没有可用索引时**才必须强制过滤。

  > 修订记录（2026-11-19）：本条原写作「三千万级表必须带过滤条件」。实际使用中该限制让
  > 运维点开表只看到「请先输入过滤条件」，无法判断表里有没有数据，属于把安全护栏做成了可用性事故。
  > 主键索引反向扫描 + `LIMIT` 的代价是与页大小同阶的，不是全表扫描，因此放宽；
  > `requireFilter` 机制保留给「排序键无索引」的表。

### Chrome 86、Windows 与部署兼容性

- 表格使用项目现有组件与设计 Token，不使用 `:has()`、`:is()` 多参、`dvh`；
- 不使用需要 104+ 的媒体查询区间语法；
- 前端只做上一页/下一页，不做任意页码跳转（与游标分页一致）；
- 无新增部署组件，仍为 Windows 单机 + Nginx + 单体 JAR。

## 迁移方案

按阶段推进，每阶段可独立回滚。

1. **阶段 0（先行，不写代码）**：为 DBA 配置 PostgreSQL 只读账号并记录在运维手册，覆盖最紧迫的查看需求。此阶段结束后重新评估是否仍需内置功能。
2. **阶段 1（后端骨架）**：`Permissions` 增加 `SYSTEM_DB_BROWSE` 并加入 `ALL_PERMISSIONS`；新增注册表、只读数据源、Service 与三个端点；开关默认关闭；补单元与 PostgreSQL 集成测试。
3. **阶段 2（审计与授权）**：接入浏览审计；在角色授权界面开放新权限；灰度给 1–2 个运维账号。
4. **阶段 3（前端页面）**：运维中心新增页面，菜单按 `system:db:browse` 显示；开关关闭时页面显示「功能未开启」且不展示任何数据行；补 Vitest 与 Chrome 86 检查。

不需要新增 Flyway 迁移：权限是常量，授权数据通过现有角色配置写入。若审计复用 `access_log` 无法承载结构化字段，才新增前向迁移建审计表，且不得回写历史迁移。

## 回滚与前向修复

- 一级回滚：关闭功能开关，前端入口隐藏、接口返回 404 语义，数据链路立即断开，无需发版。
- 二级回滚：从角色中移除 `system:db:browse`，保留代码但无人可访问。
- 三级回滚：回退版本，删除端点与前端路由；审计记录保留不删。
- 若发生误暴露：立即关闭开关 → 按 `access_log` 与业务审计定位受影响账号与时间窗 → 收紧注册表 → 按安全事件流程上报。不回写历史审计，不删除证据。

## 验证

- 单元测试：注册表查找与规范化、脱敏策略、排序/过滤白名单校验、游标编解码、开关分支、权限组合。
- PostgreSQL 集成测试：只读事务生效、`statement_timeout` 生效、`reltuples` 估算路径、keyset 翻页正确性、大表首屏可用且翻页依赖游标。
- E2E 或手工流程：无权限账号 403、有权限账号可查、敏感列掩码、拒绝场景写审计。
- 性能与容量：在等量副本上测首次查询 P95 与连接池占用，确认不影响业务接口。
- 生产或灰度验证：先灰度 1–2 个账号，观察一周审计量与耗时分布。

## 实施进展（2026-11-19）

状态：阶段 1–3 已实现，随本 PR 合并；开关默认 `false`，合并后需显式打开并授权才可用。

已落地：

- 权限 `system:db:browse` 与错误码 3001–3007；
- 注册表与定义校验（非法定义只禁用单表并告警，不阻断启动）；
- 三个只读端点，开关 `app.operations.db-browse-enabled` 默认关闭；
- 脱敏、游标分页（游标内含排序方向，方向不符按 3006 拒绝）、时间参数类型转换；
- 浏览审计日志覆盖成功与拒绝两种结果，摘要只记列名与操作符；
- 后端单元测试 + 4 个 PostgreSQL 集成测试，全量 `mvn test` 通过；
- 前端 API 模块与「数据表浏览」页面（路由 `system:db:browse`，不启用 KeepAlive）。

与规划的偏差：

- 未新建独立只读连接池，改用业务数据源 + 专用 `JdbcTemplate`（`queryTimeout=3s`）+ 只读事务，原因见接口契约 8.1；
- `orderBy` 阶段一限定在 `keyColumns` 内，保证 keyset 翻页不丢行；
- 掩码列（`CODE`/`NAME`/`ID_CARD`/`PHONE`/`PATH`）不开放 `PREFIX` 过滤：过滤在库内按原值匹配，前缀匹配等于给掩码开一条「逐字符逼近原值」的旁路。代价是病案号、上架号必须输入完整值才能查。

尚未验证：

- Chrome 86 真机渲染（仅通过类型检查、lint 与构建产物检查）；
- 灰度账号的真实使用与审计量；
- 生产库空闲连接与 IO 余量。

## 修订记录：默认姿态改为开启（2026-11-19）

- 关联 Issue：#621
- 变更：功能总开关 `app.operations.db-browse-enabled` 的默认值由 `false` 改为 `true`
  （`@Value` 兜底与 `application.properties` 同步），标准部署开箱可用；**关闭能力保留**，
  显式设 `APP_OPERATIONS_DB_BROWSE_ENABLED=false` 并重启即可即时停用，端点仍按契约返回
  `404 + 3007`，不暴露任何表信息。
- 理由：#618 落地后默认关闭使运维在标准部署下无法自助使用，需额外配置与重启；实际排障
  场景中该功能是替代登录服务器 psql 的受控入口，默认开启不改变其访问控制强度。
- 风险与缓解：拿掉「默认关闭」这层纵深后，仍保留 `system:db:browse` 独立权限（不随
  `system:read` 继承）、表级白名单与启用位、列级脱敏、只读事务 + 3s 语句超时、游标分页
  预算、`Cache-Control: no-store`、成功与拒绝的全量审计。管理员绕过与生产库容量仍是
  「后续事项」中的未决项，需在试点期收敛。
- 前端同步：功能关闭时页面显示「该功能未开启，请联系管理员」，不再把 Axios 原生
  `Request failed with status code 404` 抛给用户（`describeBrowseError`）。
- 回滚：设置环境变量 `APP_OPERATIONS_DB_BROWSE_ENABLED=false` 并重启即可回到关闭态；
  代码级回滚为 revert 对应 squash 提交，不涉及迁移或数据变更。
