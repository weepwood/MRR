# MRR 架构决策记录（ADR）

ADR 用于记录会长期约束后续开发的重要技术与业务决策，避免人员或 AI 在缺少历史背景时反复推翻既有边界。

## 何时必须写 ADR

出现以下任一情况时，应在实现前或同一 PR 中新增 ADR：

- 改变模块职责、依赖方向或公共接口；
- 引入新的数据库、缓存、中间件、外部服务或部署组件；
- 改变认证、权限、审计、外部调阅或敏感数据策略；
- 改变数据库迁移、数据一致性、导入导出或大表处理策略；
- 建立将被多个模块复用的新基础设施；
- 明确放弃一个看似合理、未来可能被再次提出的方案；
- 修改本治理规范中列出的项目不变量。

普通 Bug 修复、局部 UI 调整、依赖补丁和不改变边界的内部重构通常不需要 ADR。

## 编号与文件名

使用四位递增编号：

```text
0001-use-modular-monolith.md
0002-proxy-medical-images-through-backend.md
```

标题使用简短英文文件名，正文使用中文。编号一旦合并不得复用。

## 状态

- `Proposed`：提案中；
- `Accepted`：已经接受并约束后续实现；
- `Superseded`：被新的 ADR 替代；
- `Deprecated`：不再推荐，但可能仍为兼容而保留；
- `Rejected`：经评估未采用，用于阻止重复讨论。

被替代的 ADR 不删除，在原文中链接新的 ADR。

## 审查要求

ADR 必须说明：

- 背景和问题；
- 决策；
- 不变量；
- 替代方案及未采用原因；
- 正面和负面影响；
- 迁移与回滚；
- 验证方式；
- 关联 Issue/PR。

模板见 `0000-template.md`。
