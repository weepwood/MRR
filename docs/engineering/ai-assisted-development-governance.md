# MRR AI 辅助开发严格治理规范

## 1. 目的

MRR 是面向医疗影像、病案数据、权限审计和内网部署的生产型项目。AI 可以提高调查、编码、测试和文档效率，但不能替代需求确认、风险判断、架构决策、真实环境验证和最终责任。

本规范的目标不是要求 AI 每次都写出完美代码，而是让错误被限制在小范围内，并能被测试、门禁、审查和回滚机制尽早发现。

## 2. 基本原则

1. **证据优于声称。** “已完成”“无问题”“测试通过”必须附实际命令、结果或运行证据。
2. **边界优于速度。** 单个 PR 只解决一个主要问题，不夹带无关重构。
3. **不变量优于实现细节。** 权限、审计、数据一致性、迁移不可变和隐私边界必须先明确。
4. **真实环境优于模拟假设。** PostgreSQL、Windows Server、Chrome 109、Nginx、NAS/OSS 等关键行为不能仅靠内存数据库或 Mock 推断。
5. **前向修复优于改写历史。** 已发布 Flyway 版本迁移不得修改、重命名或删除。
6. **独立审查优于自我确认。** 实现者不能仅凭同一上下文自行宣布代码可以合并。
7. **渐进治理。** 硬性规则只覆盖不可妥协的底线；规模、测试缺口等启发式规则先警告，再根据稳定性升级为门禁。

## 3. 风险等级

| 等级 | 典型范围 | 合并要求 |
| --- | --- | --- |
| P0 | 生产故障、数据损坏、严重安全或隐私风险 | 优先止损；必须有复现、修复、回滚和生产验证方案 |
| P1 | 登录权限、审计、数据库迁移、删除导出、外部调阅、发布链路 | 必须有 Issue/变更提案、失败路径测试、独立审查和明确回滚 |
| P2 | 重要功能、跨模块改造、性能或兼容性风险 | 必须有验收标准、测试计划和影响说明 |
| P3 | 低风险 UI、文档、测试或内部整理 | 可简化方案，但仍需范围、验证和回滚说明 |

风险等级取最高影响，而不是按代码行数判断。十行权限代码可能是 P1，一千行纯文档仍可能是 P3。

## 4. 进入编码前的任务包

除明确的低风险小修外，AI 开始修改代码前必须形成以下任务包：

- 问题与证据；
- 目标；
- 明确不处理的内容；
- 必须保持的不变量；
- 影响模块、接口、表、配置和部署方式；
- 验收标准；
- 测试与手工验证计划；
- 回滚和数据修复方案；
- 尚未确认的事实或假设。

涉及数据库、权限、安全、架构、部署、外部接口或大规模数据时，使用“高风险变更提案” Issue Form。

## 5. AI 开发流程

### 5.1 调查

AI 先只读分析，不直接修改：

- 定位相关入口、调用链、数据表、测试和历史决策；
- 搜索已有工具、组件和同类实现，避免建立第二套机制；
- 区分事实、推断和未知项；
- 识别权限、审计、并发、事务、性能、迁移和兼容性风险。

### 5.2 计划

计划至少精确到文件或模块，并说明：

- 每一步修改什么；
- 为什么在这里修改；
- 如何验证；
- 如何避免扩大范围；
- 哪些步骤可以独立提交和回滚。

### 5.3 测试先行

权限、状态机、数据转换、数据库规则、并发、重试、缓存、审计、路径解析和安全逻辑优先使用 RED-GREEN-REFACTOR：

1. 先写能证明问题的失败测试；
2. 用最小实现使测试通过；
3. 在测试保护下整理代码；
4. 再执行相关集成或 E2E 验证。

### 5.4 小范围实现

- 一个 PR 只包含一个主要目标；
- 不把业务功能、全局格式化和大规模重构混合；
- 不为未来可能需求预先建立抽象；
- 发现相邻问题时创建 Issue，不顺手扩张；
- 变更超过 50 个文件或约 1500 行增删时，默认要求解释为何不能拆分。

### 5.5 独立审查

实现完成后至少进行两层审查：

1. **规格审查：** 是否满足 Issue、验收标准和非目标；
2. **代码审查：** 是否存在错误、重复机制、兼容破坏、无界查询、N+1、并发、事务、权限或隐私问题。

独立审查应尽量使用不同上下文，直接从 Issue、diff、测试和架构规范出发，而不是重复实现者的结论。

### 5.6 验证完成

PR 中记录实际执行的命令和结果。关键变更还应提供：

- 页面或请求前后对比；
- 权限拒绝和异常路径；
- PostgreSQL 迁移与事务验证；
- 日志、Trace ID 或审计记录；
- Chrome 109 / Windows PowerShell 5.1 兼容验证；
- 回滚或功能关闭验证；
- 性能基线或查询计划（适用时）。

## 6. MRR 不变量

以下规则默认不可突破；确需改变时必须先记录 ADR 和迁移方案：

- 所有医疗影像和病案访问必须经过身份、权限或受控外部票据校验；
- 已分类影像不得被自动分类静默覆盖；
- 正式类型变更、下载、导出和外部调阅必须保留可信审计；
- 医疗影像、下载包和敏感响应不得使用公共缓存；
- 已发布 Flyway 版本迁移不得修改、重命名或删除；
- 数据库结构变化必须通过新的迁移前向演进；
- 真实患者信息、密码、Token、密钥和生产内网细节不得进入代码、Issue、PR、日志、截图或 CI Artifact；
- `main` 是唯一正式主分支，正式变更必须通过 PR；
- 正式部署边界是医院内网 Windows 单机，不因局部需求擅自引入微服务、Kafka、Redis 或额外运维组件；
- 前端关键流程必须保持 Chrome 109 兼容；
- 无 Token 请求默认拒绝，兼容模式必须显式开启、只读、限 IP、限接口并可审计。

## 7. 自动门禁与人工判断

### CI 阻塞

`governance-gate` 当前阻塞：

- 新 PR 缺少必填治理章节；
- 没有关联 Issue，也没有明确无关联理由；
- 没有 P0-P3 风险等级；
- 修改、重命名或删除既有 Flyway 版本迁移；
- 提交本地配置、私钥、证书密钥库或凭据文件。

### CI 警告

第一阶段只警告：

- PR 同时跨越三个及以上工程域；
- 变更超过 50 个文件或约 1500 行增删；
- 后端业务代码变化但未同步修改后端测试；
- 前端源码变化但未同步修改前端测试。

警告不代表一定错误，但 PR 必须解释原因和替代证据。稳定观察后，可将高价值规则升级为阻塞。

### 必须人工判断

CI 不能可靠判断：

- 需求是否正确；
- 架构抽象是否必要；
- 测试是否真正覆盖风险；
- SQL 是否适合 3000 万级数据；
- 权限模型和审计语义是否符合业务；
- 页面体验和真实医院流程是否合理；
- 回滚方案在当前生产数据上是否可执行。

## 8. 数据库与迁移

- 新结构必须新增 `V...__description.sql`；
- 已合并到 `main` 的版本迁移视为不可变；
- 错误迁移使用新的前向修复迁移；
- 迁移 PR 必须说明新库、已有库、失败中断和重复启动行为；
- 复杂 Mapper、PostgreSQL 专有语法、锁和事务必须使用 PostgreSQL 16 集成测试；
- 大表 DDL 必须评估锁时间、索引构建、磁盘空间和回退方式；
- 数据修复脚本必须可审计、可分批、可重试，并先提供只读统计模式。

## 9. 合并规则

满足以下条件后才可合并：

- Issue 和 PR 边界一致；
- 所有必须检查成功；
- Review 对话已解决；
- P0/P1 有独立审查；
- 数据库、权限、审计和隐私影响已明确；
- 未执行测试有合理说明和替代证据；
- 回滚方案可执行；
- 没有把未知项伪装成已确认事实。

默认使用 squash merge，提交说明使用中文并能够独立说明变更目的。

## 10. 规则维护

治理规则本身也必须接受审查。发现误报时优先：

1. 用测试复现误报；
2. 缩小规则范围；
3. 将启发式规则降为警告；
4. 记录规则变化原因；
5. 不通过直接删除门禁来临时绕过问题。
