# MRR AI 辅助开发严格治理规范

## 1. 目的

MRR 是面向医疗影像、病案数据、权限审计和内网部署的生产型项目。AI 可以提高调查、编码、测试和文档效率，但不能替代需求确认、风险判断、架构决策、真实环境验证和最终责任。

本规范的目标不是要求 AI 每次都写出完美代码，而是让错误被限制在小范围内，并能被测试、门禁、审查和回滚机制尽早发现。

## 2. 基本原则

1. **证据优于声称。** “已完成”“无问题”“测试通过”必须附实际命令、结果或运行证据。
2. **边界优于速度。** 单个 PR 只解决一个主要问题，不夹带无关重构。
3. **不变量优于实现细节。** 权限、审计、数据一致性、迁移不可变和隐私边界必须先明确。
4. **真实环境优于模拟假设。** PostgreSQL、Windows Server、Chrome 86、Nginx、NAS/OSS 等关键行为不能仅靠内存数据库或 Mock 推断。
5. **前向修复优于改写历史。** 已发布 Flyway 版本迁移不得修改、重命名或删除。
6. **独立审查优于自我确认。** 实现者不能仅凭同一上下文自行宣布代码可以合并。
7. **渐进治理。** 硬性规则只覆盖不可妥协的底线；规模、测试缺口等启发式规则先警告，再根据稳定性升级为门禁。

## 3. 风险等级

| 等级 | 典型范围 | 合并要求 |
| --- | --- | --- |
| P0 | 生产故障、数据损坏、严重安全或隐私风险 | 优先止损；必须有复现、修复、回滚和生产验证方案 |
| P1 | 登录权限、审计、数据库迁移、删除导出、外部调阅、发布链路 | 必须有 Issue/变更提案、失败路径测试、独立审查和明确回滚 |
| P2 | 重要功能、跨模块改造、性能或兼容性风险 | 必须有验收标准、测试计划和影响说明 |
| P3 | 低风险 UI、文档、测试或内部整理 | 可简化方案，但仍需范围、验证和回滚说明 |

风险等级取最高影响，而不是按代码行数判断。十行权限代码可能是 P1，一千行纯文档仍可能是 P3。

## 4. 进入编码前的任务包

除明确的低风险小修外，AI 开始修改代码前必须形成以下任务包：

- 问题与证据；
- 目标；
- 明确不处理的内容；
- 必须保持的不变量；
- 影响模块、接口、表、配置和部署方式；
- 验收标准；
- 测试与手工验证计划；
- 回滚和数据修复方案；
- 尚未确认的事实或假设。

涉及数据库、权限、安全、架构、部署、外部接口或大规模数据时，使用“高风险变更提案” Issue Form。

## 5. AI 开发流程

### 5.1 调查

AI 先只读分析，不直接修改：

- 定位相关入口、调用链、数据表、测试和历史决策；
- 搜索已有工具、组件和同类实现，避免建立第二套机制；
- 区分事实、推断和未知项；
- 识别权限、审计、并发、事务、性能、迁移和兼容性风险。

### 5.2 计划

计划至少精确到文件或模块，并说明：

- 每一步修改什么；
- 为什么在这里修改；
- 如何验证；
- 如何避免扩大范围；
- 哪些步骤可以独立提交和回滚。

### 5.3 测试先行

权限、状态机、数据转换、数据库规则、并发、重试、缓存、审计、路径解析和安全逻辑优先使用 RED-GREEN-REFACTOR：

1. 先写能证明问题的失败测试；
2. 用最小实现使测试通过；
3. 在测试保护下整理代码；
4. 再执行相关集成或 E2E 验证。

### 5.4 小范围实现

- 一个 PR 只包含一个主要目标；
- 不把业务功能、全局格式化和大规模重构混合；
- 不为未来可能需求预先建立抽象；
- 发现相邻问题时创建 Issue，不顺手扩张；
- 变更超过 50 个文件或约 1500 行增删时，默认要求解释为何不能拆分。

### 5.5 独立审查

实现完成后至少进行两层审查：

1. **规格审查：** 是否满足 Issue、验收标准和非目标；
2. **代码审查：** 是否存在错误、重复机制、兼容破坏、无界查询、N+1、并发、事务、权限或隐私问题。

独立审查应尽量使用不同上下文，直接从 Issue、diff、测试和架构规范出发，而不是重复实现者的结论。

### 5.6 验证完成

PR 中记录实际执行的命令和结果。关键变更还应提供：

- 页面或请求前后对比；
- 权限拒绝和异常路径；
- PostgreSQL 迁移与事务验证；
- 日志、Trace ID 或审计记录；
- Chrome 86 / Windows PowerShell 5.1 兼容验证；
- 回滚或功能关闭验证；
- 性能基线或查询计划（适用时）。

## 6. MRR 不变量

以下规则默认不可突破；确需改变时必须先记录 ADR 和迁移方案：

- 所有医疗影像和病案访问必须经过身份、权限或受控外部票据校验；
- 已分类影像不得被自动分类静默覆盖；
- 正式类型变更、下载、导出和外部调阅必须保留可信审计；
- 医疗影像、下载包和敏感响应不得使用公共缓存；
- 已发布 Flyway 版本迁移不得修改、重命名或删除；
- 数据库结构变化必须通过新的迁移前向演进；
- 真实患者信息、密码、Token、密钥和生产内网细节不得进入代码、Issue、PR、日志、截图或 CI Artifact；
- `main` 是唯一正式主分支，正式变更必须通过 PR；
- 正式部署边界是医院内网 Windows 单机，不因局部需求擅自引入微服务、Kafka、Redis 或额外运维组件；
- 前端关键流程必须保持 Chrome 86 兼容；
- 无 Token 请求默认拒绝，兼容模式必须显式开启、只读、限 IP、限接口并可审计。

## 7. 自动门禁与人工判断

### CI 阻塞

`governance-gate` 当前阻塞：

- 新 PR 缺少必填治理章节（P3 保留变更、关联、风险、验证、回滚五节，可省略 AI 参与报告）；
- P0/P1 没有关联 Issue/提案，或 P2/P3 既没有关联 Issue 也没有明确无关联理由；
- 没有 P0-P3 风险等级；
- 修改、重命名或删除既有 Flyway 版本迁移；
- 提交本地配置、私钥、证书密钥库或凭据文件。

### CI 警告

第一阶段只警告：

- PR 同时跨越三个及以上工程域；
- 变更超过 50 个文件或约 1500 行增删；
- 后端业务代码变化但未同步修改后端测试；
- 前端源码变化但未同步修改前端测试。

警告不代表一定错误，但 PR 必须解释原因和替代证据。稳定观察后，可将高价值规则升级为阻塞。

### 必须人工判断

CI 不能可靠判断：

- 需求是否正确；
- 架构抽象是否必要；
- 测试是否真正覆盖风险；
- SQL 是否适合 3000 万级数据；
- 权限模型和审计语义是否符合业务；
- 页面体验和真实医院流程是否合理；
- 回滚方案在当前生产数据上是否可执行。

## 8. 数据库与迁移

- 新结构必须新增 `V...__description.sql`；
- 已合并到 `main` 的版本迁移视为不可变；
- 错误迁移使用新的前向修复迁移；
- 迁移 PR 必须说明新库、已有库、失败中断和重复启动行为；
- 复杂 Mapper、PostgreSQL 专有语法、锁和事务必须使用 PostgreSQL 16 集成测试；
- 大表 DDL 必须评估锁时间、索引构建、磁盘空间和回退方式；
- 数据修复脚本必须可审计、可分批、可重试，并先提供只读统计模式。

## 9. 合并规则

满足以下条件后才可合并：

- Issue 和 PR 边界一致；
- 所有必须检查成功；
- Review 对话已解决；
- P0/P1 有独立审查；
- 数据库、权限、审计和隐私影响已明确；
- 未执行测试有合理说明和替代证据；
- 回滚方案可执行；
- 没有把未知项伪装成已确认事实。

默认使用 squash merge，提交说明使用中文并能够独立说明变更目的。

CI 按 [分层 CI 与发布验收](ci-tiered-verification.md) 执行。普通 PR 只对改动范围进行必要检查；
数据库、权限等高风险路径仍在合并前验证；完整覆盖率、生产候选包和 Windows 恢复在创建 tag 前验收。
分支保护迁移后仅要求 governance/pr-gate 两个稳定状态，不能用减少状态名称来伪造测试成功。

## 10. Git 分支与 worktree 管理

### 10.1 工作区对应关系

- 每个独立任务使用一条分支和一个专属 worktree；并行任务不得共用工作区，以免提交边界和未提交改动相互污染。
- `main` 是唯一正式主分支。建议保留固定的 `main` worktree 仅用于同步与检查；功能开发从最新 `origin/main` 创建任务分支。
- AI 开始分支工作时，应记录任务或 Issue、关联 PR、分支名、worktree 绝对路径及状态。状态统一为“进行中、待合并、已完成、待认领”。无 Issue 时不得杜撰编号，需在 PR 中说明无 Issue 的原因。

### 10.2 命名约定

新分支使用类型前缀和简短主题，优先关联 Issue 编号：

```text
codex/<issue>-<topic>
feat/<issue>-<topic>
fix/<issue>-<topic>
docs/<issue>-<topic>
test/<issue>-<topic>
perf/<issue>-<topic>
```

例如 `codex/462-portrait-login`。已有分支无需仅为统一命名而批量改名；新建分支遵守本约定即可。

### 10.3 盘点和清理前置检查

用户要求盘点或清理分支时，AI 必须先只读生成清单，至少包含：本地/远程分支名、上游关系与领先/落后数、独有提交、关联 PR 状态和 head SHA、worktree 路径、worktree 是否有未提交改动、最近提交时间及建议动作。建议动作限定为保留、待确认、可清理；不得只按分支年龄自动判断。

在删除任何本地分支或 worktree 前：

1. 确认目标不是 `main`，也没有被其他 worktree 使用；
2. 检查目标 worktree 是否存在未提交、未跟踪或未保存改动；
3. 确认所有独有提交已合并、已另行保存，或经用户明确决定放弃；
4. 核对 PR 状态和合并后的目标内容；
5. 先列出拟执行的清理项，再执行并复查剩余状态。

有未提交改动时必须停止对该 worktree/分支的清理并报告，不得擅自 stash、提交、重置、清理文件或强制移除。没有 worktree、落后 `main`、长期未更新或远程跟踪分支已消失，均不足以单独证明分支可删除。未合并且归属不明的分支标记为“待认领”，保留并请求用户决定。

### 10.4 合并后的生命周期

- PR 合并并确认 worktree 干净后，可移除专属 worktree 和本地分支；普通情况使用安全删除 `git branch -d`。
- 本项目默认 squash merge。若分支提交因 squash/rebase 未成为目标分支祖先，只有在确认 PR 已合并、PR head SHA 与目标一致且变更已包含、worktree 干净且无人使用后，才可删除该本地分支；记录核验依据。不能仅因 PR 显示已关闭就跳过内容核对。
- 远程分支优先由 GitHub 的合并后自动删除策略处理；除用户明确要求或仓库策略要求外，AI 不主动删除远程分支。
- `git fetch --prune` 只移除失效的远程跟踪引用，不删除远程分支。`git worktree prune` 只用于清理确认路径已不存在的孤立登记；执行前核实路径，不用于处理活跃 worktree。
- 不批量删除陌生分支，不对 `main` 使用 reset/强制更新。同步 `main` 使用 `git fetch origin` 后的 fast-forward；若不能快进，停止并调查分歧。

清理完成后，报告已删除的 worktree/本地分支、保留的分支及原因、`main` 状态，以及仍含未提交改动的 worktree。用户要求“精简分支”时，默认只处理证据充分且干净的本地对象，不将未提交内容擅自塞入其他 PR。

## 11. 规则维护

治理规则本身也必须接受审查。发现误报时优先：

1. 用测试复现误报；
2. 缩小规则范围；
3. 将启发式规则降为警告；
4. 记录规则变化原因；
5. 不通过直接删除门禁来临时绕过问题。
