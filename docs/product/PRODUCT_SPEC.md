## 1. 产品定义

### 1.1 名称与定位

**产品名称：MRR（Medical Record Repository，医疗病案与影像档案管理平台）**。

面向医院院内病案管理、扫描记录、数字化影像归档、查询调阅、受控导出、实体档案关联和数据运维的业务平台，优先解决“找得到、看得全、查得清、访问受控、出错可追溯”的历史病案使用问题。

**不是** DICOM/PACS 诊断工作站；首轮不提供窗宽窗位、医学测量、多帧诊断回放、AI 医疗诊断结论，也不扩展为互联网多租户 SaaS。

### 1.2 核心业务问题

1. 大规模历史记录中，病案号、上架号、患者身份和扫描记录可能存在历史编码、歧义、空结果或关联缺口。
2. 同一病案图片可能位于本地/NAS、Nginx/HTTP 与 OSS，调阅必须有统一权限、明确缺失/故障语义。
3. 下载、打印、PDF 和 ZIP 的资源占用、后台任务与旧浏览器适配存在上线风险。
4. 医院需要可信的操作审计、故障诊断、回滚与恢复，而不是仅有前端“成功”提示。
5. 现有产品能力多而分散，需要围绕实际任务重排信息层级和验收优先级。

### 1.3 产品原则

- **医疗隐私优先于便利**：最小权限、默认拒绝、后端授权、私有缓存与脱敏证据。
- **原始数据优先于猜测修复**：不自动补零、不猜测病案归属、不用无证据的“自动修复”掩盖冲突。
- **任务成功与文件成功分开**：生成完成、下载完成、文件可打开、现场交付不是同一个状态。
- **显式错误优于空白**：无结果、歧义、来源不可用、权限拒绝、任务过期都应可区分。
- **现有架构优先**：不因局部功能另建身份、任务队列、文件服务、状态管理或 UI 设计系统。
- **现场证据优于宣传指标**：医院真实数据、副本、Chrome 86、Windows/Nginx/存储链路必须有可复现记录。

## 2. 目标人群、权限与使用边界

| 角色 / 场景 | 核心任务 | 使用范围 |
| --- | --- | --- |
| 院内病案检索与调阅人员 | 查询患者、识别准确病案、阅读扫描影像、按授权打印/导出 | 最小授权的 `record:read`、`record:download`、`record:pdf:export` |
| 病案管理/数据整理人员 | 管理扫描记录、病案类型、档案装箱、数据质量与导入导出 | 按真实业务授权，敏感修改须审计 |
| 系统管理员 | 用户审核、角色授权、来源与系统配置、维护模式 | `user:manage` / `system:read` 等按接口授予 |
| 运维/审计人员 | 查看服务状态、访问日志、错误、任务和恢复证据 | `log:read` / `system:error:read` 等，不能自动获患者数据权限 |
| HIS/EMR 发起方及院内工作站 | 从外部业务上下文直接打开限定病案的只读档案袋 | 后端 HMAC Ticket → 有效受限 Session；默认禁止下载 |

角色是业务画像，不等于新增一组固定 `DOCTOR/NURSE/ADMIN` 数据库角色。**最终以现有 RBAC、后端权限拦截器和接口测试为准**；前端按钮隐藏不是授权。

## 3. 产品目标、范围与里程碑

### 3.1 首轮院内目标（历史病案调阅试点）

用户在院内认证后，从病案号/上架号/经授权的身份证入口定位病案，核对元数据和影像数量，分类浏览与全屏查看，按权限选择、打印或导出；出现歧义、空结果、源故障、下载失败时可安全恢复并保留审计。

**首轮必须具备：**
1. 可解释、无静默补零的精准查询和错误状态；
2. 分类浏览、缩略图与全屏预览，混合图片来源的逐项故障提示；
3. 细粒度读取、打印/下载/PDF 授权与完整审计；
4. 可取消、可追踪、有大小/张数预算的下载导出，不加载无界大病案；
5. 运维健康检查、恢复机制、真实医院副本验收与安全回滚。

**不纳入首轮**：新扫描业务闭环、批量自动改类、完整生命周期系统、Manifest 全链路、多 GB 无限制下载、HIS 正式联调和诊断级图像处理。

### 3.2 版本与状态

| 阶段 | 产品结果 | 状态 / 准入门槛 |
| --- | --- | --- |
| **A：v0.8.0 主线基线** | 患者/扫描/统计、档案袋、异步 ZIP/PDF、权限审计、存储降级、外部 Ticket、运维能力 | **基线已有**；不等于医院现场已通过 |
| **B：首轮受控上线候选** | 历史病案调阅、稳定打印、受限 ZIP/PDF、Chrome86 兼容 | **待整合/待现场验收**；#350 和 #504/#527/#528 的发布前证据不能跳过 |
| **C：业务闭环强化** | 关系质量基线、档案核对/归档与实体位置流程、受控修复工单 | **后续规划**；先证实主线缺口和迁移可行性 |
| **D：智能和跨系统能力** | OCR 人工审核、检索辅助、HIS/EMR 正式联调、超大档案分卷/续传 | **后续规划**；独立风险评估，不绑入首轮 |

## 4. 核心业务流程（场景规格）

### PS-01 病案检索与确认（P0）

**前置条件**：有效院内会话及 `record:read`；采用当前检索服务和响应隔离。

**流程**：进入“病案检索” → 输入 BAH、SJH 或获授权身份证 → 前端仅做格式提示 → 服务端精确解析 → 返回唯一病案或明确原因 → 显示病案摘要、影像数与来源状态 → 进入档案袋。

**强制业务规则：**
- `bah`、`sjh` 仅去除首尾空格，**不自动补零**；`123` 与 `00000123` 不视为相同字符串。
- BAH 小于 `10000000` 时可单独查询；大于或等于时**必须**同时提供 SJH。
- 非空且唯一的 SJH 可单独定位；歧义或缺少关键条件不允许猜测返回第一条。
- 身份证入口须走当前安全查询链路；成功后地址栏不保留身份证原文。
- 翻页和快速连续查询只展示当前提交条件对应的结果；迟到响应不能覆盖新病案。

**异常状态**：未填、格式错、歧义、无记录、记录有但影像缺失、权限不足、超时、来源异常必须分开表达。对未授权者不能泄露病案是否存在。

**验收**：合成夹具覆盖低位/高位 BAH、前导零、唯一/重复 SJH、缺失图片、401/403、双会话与慢响应交错；真实数据在授权隔离副本按 #350 复核。

### PS-02 影像档案袋浏览（P0）

**前置条件**：已定位病案、具有读权限或有效受限外部 Session。

**流程**：展示病案摘要与数量 → 按类型/页序导航 → 切换缩略图/列表/全屏 → 查看单张的加载/缺失情况 → 必要时切换已授权来源重试。

**交互与性能约束**：
- 使用现有 `/archive`、`/archive/embed` 与外部专用入口；不另建鉴权或图像直连通道。
- 缩略图优先可见范围加载，非可见图片不无界下载；大案分页/虚拟化按现有组件能力复核。
- 图片显示自然比例、支持适合窗口/原图比例、左右切换、键盘关闭与焦点恢复；水印遵循现有权限和配置。
- 来源故障时提供“重试、查看诊断编号、返回列表”，不暴露原始绝对路径、OSS Key 或签名链接。
- 分类显示使用既有病案类型字典 **0～15**；未分类 0 不等于自动识别结果。
- 后台图像加载与选择交互必须保持病案身份隔离，切换病案后旧内容不得闪现。

**验收**：合成混合 OSS/Nginx/NAS/本地病案、单张 404/超时、签名过期、导航边界、并发切案、键盘与减少动态效果；真实来源、Chrome86 在 #350 验收。

### PS-03 打印、PDF 与 ZIP（P0，P1 上线风险）

**前置条件**：内网账号和对应导出授权；外部 Ticket 默认无下载能力。后端始终重新校验当前用户、病案范围、有效影像、配额和任务所有者。

**流程**：选择影像或整案 → 预检数量/大小与可用性 → 根据操作发起打印、PDF 或后台 ZIP/PDF 任务 → 展示“排队/处理中/生成完成/下载中/已下载/失败/取消/过期” → 可取消、失败后按权限重新下载或重新创建。

**首轮资源预算属于待发布方案，不是 v0.8.0 默认事实**：
- #517 等候选设计：单个文件 **128 MiB**、单次打印 **50 张**，超限整体拒绝并提示分批；未知输出大小不能直接走无界整份 Blob。
- 预算前后端必须在**同一候选版本**闭环。仅后端配置提高上限不能绕过客户端限制。
- 已生成成功但下载失败，应保留“文件已生成，下载未完成”的独立提示与可重试入口。
- 取消、切页、离开页面、网络失败、任务过期、Range 断点恢复以及旧请求迟到须有明确且不越权的状态行为；浏览器已提交的物理文件写入不承诺能撤销。
- 普通 HTTP/权限拒绝/预算拒绝不得静默回退到整包无界下载。

**验收**：与 #504、#171、#527/#528 的实际合入 SHA 同步核对。分别验证权限 403、空选择、重复点击、取消/完成竞争、资源超限、生成成功下载失败、Range 恢复、Chrome86 无文件句柄 API、HTTP/Nginx 中断、混合来源及文件可打开；现场记录资源峰值。

### PS-04 用户登录与权限管理（P0）

**流程**：登录/注册申请 → 管理员审批或建号 → 首次改密 → 获得会话与权限 → 访问相应模块 → 退出/停用/改密后权限及时收敛。

**不可变规则**：使用现有 JWT、bcrypt、密码版本、账号状态和 RBAC；无 Token 默认 401，授权不足 403；已撤销 Token 在重启后仍须按现有策略拒绝。兼容模式默认关闭，管理员不能以 UI 显示代替授权。

**验收**：新注册未审核、禁用用户、首次改密、权限实时变化、登出/超时/重启撤销、非法或过期 Token 与跨权限读取/导出都应拒绝；不记录敏感凭据。

### PS-05 外部 HIS/EMR 调阅（基线已有，正式联调为后续阶段）

**流程**：HIS 已登录用户 → HIS 后端生成 HMAC 请求 → MRR 校验 Client/IP/timestamp/nonce/签名/病案范围 → 签发一次性短期 Ticket → 浏览器兑换受限 HttpOnly Session → 打开限定档案袋。

**边界**：HMAC Secret 仅存在服务器；Ticket/launchUrl 不进普通日志；不能把 HIS 前端传入的用户名当作真实操作者；默认只读、禁下载；`archives` 精确组合优于不确定条件。沿用现行接口，勿将旧无 Token 兼容模式作为新集成方案。

**验收**：过期、重放 nonce、篡改、非法来源 IP、越界病案、重复使用、外部访问审计以及会话失效拒绝。正式环境联调及业务授权单独批准。

### PS-06 数据治理、归档和 OCR（后续规划）

- 阶段 C：先形成患者/病案主档/扫描/统计/装箱的只读关联质量基线。异常给出口径与样本，不自动批量修改；修复须旧值比对、审批、批次、幂等、审计和恢复方案。
- 病案生命周期（REGISTERED / SCANNING / PENDING_REVIEW / ARCHIVED / BOXED 等）**不能仅凭已关闭的 #143 视为已进入主线**；#515/#516 已记录实现证据不足。下一步先核实实体/迁移/API，缺少的部分另立提案。
- OCR 文本、分类建议、正式影像类型必须分离；默认不开启自动覆盖既有分类；批量确认要求授权、阈值、范围、抽样复核、失败恢复。
- 不把扫描/归档闭环或 OCR 医疗诊断并入首轮历史病案调阅范围。

### PS-07 运维、审计与异常恢复（P0）

**流程**：健康/服务状态 → 运维诊断 → Request ID 关联访问、图片、下载或运行错误 → 维护/只读降级 → 按隔离副本恢复或前向修复。

**规则**：普通用户只见安全错误码与 Request ID；管理员查看脱敏诊断；健康状态必须区分未知、未检查、警告和失败；日志敏感字段脱敏、受访问控制；真实医疗记录不得出现在 CI/Issue/截图中。

**验收**：PostgreSQL 16、Nginx、NAS/OSS、磁盘满、数据库中断、Token 撤销、日志轮转/补录、备份实际恢复、只读降级的写操作拒绝，按 #350 验收包由院内受控记录签署。

## 5. 产品信息架构与页面设计规格

### 5.1 一级导航（建议按任务聚合，不要求本轮重写路由）

| 一级分组 | 推荐入口 | 组织原则 |
| --- | --- | --- |
| **工作台** | 首页、快速病案检索、最近访问（仅安全摘要） | 一眼进入高频任务，避免堆叠技术指标 |
| **病案与影像** | 患者、病案/扫描记录、影像档案袋、档案装箱 | 以“定位 → 确认 → 调阅 → 处理”为主要路径 |
| **数据与统计** | 统计、数据关系、数据交换、质量检查 | 展示统计口径/日期与扫描范围，修改入口受限 |
| **存储与任务** | OSS 迁移、只读存储浏览、后台导出任务 | 只展示用户有权访问的任务和来源 |
| **安全与运维** | 用户权限、日志/审计、错误、监控、系统设置 | 运维人员按权限见到；避免普通用户误操作 |

保留现有业务路由和授权体系，仅作为后续导航重整的产品约束。外部 Ticket 的档案袋隐藏管理导航，不展示内部系统操作。

### 5.2 核心页面：病案检索 → 影像档案袋

```text

[摘要：病案身份(按权限脱敏) | 病案号 | 上架号 | 影像数量 | 来源状态]
[类型筛选] [仅显示可用] [缩略图/列表]     [打印] [PDF] [ZIP]
┌────────────────────────────────────────────────────────┐
│  缩略图区域（异步/分段加载，明确缺图/错误态，支持选择） │

└────────────────────────────────────────────────────────┘
[详情/预览：图片序号 | 缩放/适应 | 上一张/下一张 | 关闭]
[按需任务面板：排队 → 处理中 → 已生成 → 下载中 → 已完成]
```

**布局约束**：
- 页面优先采用现有 `MrrPageShell` / `MrrSectionCard` / `MrrDataTablePanel`、全局 Token 和 Element Plus，避免第二套主题。
- 常规筛选与按钮遵循现有 **33px** 控件高度；标题、指标卡、容器圆角与间距以 `DESIGN.md` 为准；高密度信息通过分组和留白优化而非减小可读字号。
- 一级操作每个区域保持一个主按钮；危险操作独立二次确认，角色不可用的能力同时展示明确的禁用原因（不能泄露敏感状态）。
- 使用已定义的语义状态色，不依赖颜色作为唯一表达方式。加载使用低干扰进度；骨架/动画不覆盖内容和错误提示。
- 浏览器以 **Chrome 86** 作为关键流程兼容下限；CSS 新特性有回退。轻微动效使用现有时长策略，并支持 `prefers-reduced-motion`。
- 以键盘可操作、焦点可见、表单标签与错误关联、抽屉/弹层焦点恢复为最低可访问性要求；大表格不得给每一行添加进入动画。
- 设计冻结后，具体组件视觉不在产品规格中再写一套配色；视觉事实由 `frontend-fantastic-admin/DESIGN.md` 统一管理。

### 5.3 通用状态模型

| 状态 | 页面呈现与用户下一步 |
| --- | --- |
| 初始/未检索 | 展示合理输入说明和最近的非敏感帮助 |
| 查询中 | 保留提交的筛选快照、阻止同一请求重复发起 |
| 空结果 | 解释是否未匹配，允许修正条件；不显示虚假的“影像正常” |
| 歧义/编号冲突 | 引导输入更精确 BAH + SJH；不得自动选第一个 |
| 暂无可用图片 | 显示病案元数据与缺失/来源故障区别，可重试 |
| 权限拒绝 | 不展示记录是否存在，仅给 401/403 与授权处理建议 |
| 超时/网络错误 | 不清空当前已确认的数据，提供安全重试和 Request ID |
| 导出已生成但未下载 | 保持成功任务，提供授权范围内的重新下载 |
| 维护/只读降级 | 明确提示可读/不可写操作及恢复预期，不允许假成功 |

## 6. 数据、隐私与产品不变量

1. **实体边界**：患者 `mr_patient`、病案主档 `mr_archive`、扫描 `mr_scan`、统计 `mr_statistics`、实体装箱记录、导出任务与审计按当前模型维护；不按旧 PRD 的简化 ER 图推断表结构。
2. **规模边界**：`mr_scan` 约三千万级的设计量级；检索和质量分析禁止无界全表加载、大事务或用 `LIMIT` 当成 SQL 扫描有界保证。
3. **编码边界**：BAH/SJH 不补零、不自动合并；扫描种类以主线 0～15 字典为准；历史不确定关联保留异常供人工复核。
4. **完整性边界**：资料“有记录”不等于“源图片可读取”，也不等于“已完成电子归档”；统计指标必须标注分母、数据来源、范围和时间。
5. **访问边界**：所有病案/影像、导出和外部调阅通过后端授权，外部 Ticket 只赋予最小范围；禁止公开缓存医疗图片、导出文件与敏感响应。
6. **审计边界**：正式分类变更、病案数据修改、导出、下载和外部调阅记录真实操作者、时间、动作、对象、结果和 Request ID；日志不得保留秘密或不必要的患者原文。
7. **存储边界**：浏览器不得拿到生产存储凭据；路径/签名/内部 IP 不作为客户端诊断详情；迁移和删除不会静默破坏原图。
8. **迁移边界**：PostgreSQL 16、Flyway 已合并历史脚本不可修改；任何新数据修复独立立项、前向迁移、可分批、可回溯。
9. **运行边界**：正式医院 Windows Server + Nginx + 单体 Spring Boot + PostgreSQL 16；Docker 仅供开发、测试、演示。

## 7. 非功能规格和验收测量

> 这里是**建议的可测标准和测量方法**，不是主线已经通过或医院承诺的 SLO。院方应在首轮试点前批准目标值、观察窗口、硬件与副本范围。

| 维度 | 最低验收要求 | 证据与方法 |
| --- | --- | --- |
| 正确性 | 编号歧义、前导零、跨案响应隔离 **0 容忍错误匹配** | 合成夹具 + 等量授权副本 + 两个并发会话 |
| 权限与隐私 | 未认证 401、未授权 403、跨案/跨任务访问拒绝；日志无敏感原文 | 后端权限测试 + 真机回归 + 脱敏样本 |
| 查询性能 | 统计冷/热 P50/P95/P99、锁等待、索引与缓存命中；新诊断日志 P95 额外开销目标 **≤10%** | #350 同负载开关对比；无有效基线时不得声称达标 |
| 大表安全 | 查询计划与数据库超时受限，质量扫描有窗口、检查点及失败退出 | PostgreSQL16 `EXPLAIN (ANALYZE, BUFFERS)`、定向压测 |
| 影像可用 | 混合来源逐张显示、拒绝/缺失/过期提示正确，失败不泄露源路径 | Windows/Nginx/NAS/OSS 实测 |
| 导出可靠 | 生成/下载分离，取消/过期/超限/Range/重复提交可恢复，文件可打开且权限正确 | 同 SHA 单测/集成 + 真机资源与中断试验 |
| 浏览器兼容 | Chrome86 核心浏览/查询/预览/导出路径可用，降级提示准确 | 真实 Chrome86 + 静态兼容检查；静态不代替真机 |
| 可访问性 | 键盘查询/导航/关闭/确认完整、焦点可见、减少动态效果可用 | 手工键盘与 reduced-motion 回归 |
| 恢复性 | 已授权隔离空库可成功恢复并读图；RPO/RTO 按院方签字标准 | Windows PG16 真实恢复演练，不用脚本检查代替 |
| 可运维性 | 失败有脱敏错误码/Request ID、可观察作业状态、可关闭新功能 | 运行错误中心、审计和院内验收记录 |

**产品使用指标（试点后采集，仅聚合）**：成功且唯一定位病案的查询比例、首次可见影像耗时分布、无图/源错误率、导出成功与下载成功的分开比例、权限拒绝计数、平均一次调阅操作数、工单关闭时间。不得在公共遥测中收集病案号、身份证号、患者姓名、Token 或文件路径。

## 8. 交付包与阶段验收

### 阶段 A：主线事实核对（只读）

- 输出 `VERSION`、Git SHA、`release-baseline.json`、数据库迁移上限、部署配置与功能启用标志。
- 逐项标记“主线有代码/仅在 PR/后续方案/现场待验收”，避免把历史关闭 Issue 当作已实现。
- 锁定首轮业务权限、可用影像来源、院内授权副本与合成测试数据。

### 阶段 B：首轮历史病案试点（上线候选）

- 先确认 #527 / #528 所涉导出候选与依赖 PR 的真实整合、审查、必要 CI 和发布范围；不能单凭单 PR 绿灯启用。
- 在隔离 PG16 副本和医院 Windows + Nginx + Chrome86 上执行 #350；按 [验收记录模板](../engineering/hospital-replica-acceptance-record.md) 逐项记录 PASS/FAIL/BLOCKED/N/A。
- 首批场景：检索、核对、查看、切页、打印、受限 PDF/ZIP、下载恢复、401/403、来源故障、维护/只读降级、数据库备份恢复。
- 医院负责人签署准入并注明开放角色、权限、容量、观察窗口与回滚方式；未签署的能力保持关闭或限定试点。

### 阶段 C：病案数据质量与生命周期

- 先只读建立关联完整性、冲突和误归属基线；数据修复另行审批，历史数据不直接自动纠正。
- 重建 #143 的实际需求与当前主线差距；生命周期与历史审计须新的方案、迁移、授权、并发与验收，不将状态字段存在等同功能完成。
- 引入完整性 Manifest、人工核对与档案装箱时必须保证“内容验证”和“业务确认”彼此独立。

### 阶段 D：智能归类与系统集成

- OCR 先输出候选与审核记录，正式改类必须人工或受控审批；不自动替代专业医疗判断。
- HIS/EMR 先在受控环境做 Ticket 联调，再由院方授权正式接入；禁止旧无 Token 便捷访问。
- 大文件、多 GB 下载/分卷/续传需独立资源和浏览器策略评审；不得无预算开放整包内存下载。

### 统一 Definition of Done

1. 对应 Issue 说明目标、非目标、数据与权限影响、风险等级、验收、回滚；高风险修改有 Change Proposal/ADR。
2. PR 基于最新 `main` 独立分支、小范围实现，**中文提交**；产品规格、接口、前端状态、测试相互一致。
3. P0/P1 先失败用例再修复，独立审查且在**同一候选 SHA** 完成必须的 CI/集成验证；不能仅凭 Mock 宣称通过。
4. 涉及 Windows、PG16、Chrome86、Nginx、NAS/OSS 的功能提供现场副本验收或明确 BLOCKED，不可隐藏。
5. 版本、发布包和 Flyway 兼容边界明确，回滚不降低当前认证、隐私与令牌撤销基线。
6. 文档描述真实可用状态；未经签字不宣布生产上线。
