# 文档维护规范

MRR 同时维护根 README、用户手册、内部文档、实时 OpenAPI 和更新日志。文档的目标不是复制代码，而是为不同角色提供稳定入口，并明确事实来源、限制和操作风险。

## 文档分层

| 文档 | 读者 | 内容边界 |
| --- | --- | --- |
| 根 `README.md` | 项目访问者、开发者、部署人员 | 项目定位、当前能力、快速启动、部署摘要和文档入口 |
| 用户手册 | 普通用户和管理员 | 页面可见操作、权限、业务规则和常见问题 |
| 内部文档 | 开发、测试、数据库、部署和运维人员 | 架构、配置、迁移、部署、安全、运行手册和故障排查 |
| Springdoc | 接口调用方和开发者 | 当前运行版本的请求、响应和接口模型 |
| `CHANGELOG.md` | 发布与审计 | 人工整理的重要新增、变更、修复和已知限制 |
| 自动 Git 更新记录 | 维护人员 | 当前分支第一父级提交历史 |

## 事实来源优先级

发生冲突时按以下顺序处理：

1. `main` 当前代码和测试；
2. 实际 Flyway 迁移链和数据库约束；
3. `application.properties`、`VERSION`、`release-baseline.json`；
4. 运行中的 OpenAPI、Actuator 和页面权限；
5. 内部文档；
6. 用户手册；
7. 历史截图、Issue、PR 描述和旧分支说明。

尚未合并的 PR 和 Issue 不应写成当前已上线功能。可以在路线图或“计划中”章节说明，但必须明确状态。

## 哪些改动必须同步文档

### 用户可见功能

新增或修改页面、按钮、菜单、流程、权限或错误提示时，更新：

- 对应用户手册页面；
- 用户手册导航；
- `release-notes.md`；
- 必要时更新根 README 的功能表。

### API 与权限

新增接口或改变访问边界时，更新：

- 控制器 OpenAPI 注解；
- 内部 `api.md`；
- 用户手册中的权限表；
- 安全文档；
- 权限拦截器和相关 Controller 单元测试。

### 配置

新增环境变量、默认值、端口、路径、线程池、配额或密钥时，更新：

- `application.properties` 注释；
- [配置参考](./configuration-reference.md)；
- 部署模板和 Windows 示例；
- 发布基线中的配置结构版本（如适用）。

### 数据库

新增表、字段、索引、约束或迁移时，更新：

- 数据库文档；
- 数据导入与迁移文档；
- 相关用户操作说明；
- 回滚和兼容性说明。

### 部署与发布

改变 JAR、Nginx、脚本、目录、端口、服务管理或发布包结构时，更新：

- Windows 部署文档；
- 运行手册；
- 发布流程；
- 根 README 的部署摘要；
- `CHANGELOG.md`。

## 页面写作模板

每个操作页面建议包含：

1. 页面用途和权限；
2. 入口路径；
3. 前置条件；
4. 正常操作步骤；
5. 关键业务规则；
6. 状态和错误含义；
7. 安全与数据注意事项；
8. 常见问题；
9. 关联文档。

内部技术页面建议包含：

1. 事实来源和适用版本；
2. 架构或数据流；
3. 配置与默认值；
4. 正常运行流程；
5. 失败模式；
6. 观测指标和日志；
7. 回滚或恢复步骤；
8. 验证清单。

## 命令规范

文档中的命令必须说明：

- 操作系统；
- 执行目录；
- 是否需要管理员权限；
- 是否修改数据或服务；
- 是否可重复执行；
- 失败后的恢复方式。

不要把 Linux Bash 命令直接写成 Windows Server 的唯一正式部署方法。PowerShell 和 CMD 脚本要注意 UTF-8/GBK、路径空格和执行策略。

## 敏感信息规范

禁止在文档、截图和示例中包含：

- 真实身份证号和患者姓名；
- 生产数据库密码；
- JWT、AES、HMAC 密钥；
- OSS AccessKey；
- 完整 Token、Cookie 和签名 URL；
- 内网真实地址（公开文档中）；
- 可直接定位真实病案的编号组合。

示例数据应使用明显的虚构值，并保持业务格式合理。

## 链接与导航

新增文档后必须同时检查：

- 用户站点或内部站点导航；
- 相对链接；
- `srcDir` 和 `base` 影响；
- 用户手册是否错误链接内部页面；
- 内部站点是否能访问用户手册页面；
- 图片和静态资源路径；
- VitePress 构建是否报告死链接。

用户站点应使用 `ignoreDeadLinks: false`，避免新增页面后留下无效入口。

## 版本说明

- 页面标题不手工写死产品版本，优先从根 `VERSION` 读取；
- 发布说明必须标注对应版本；
- 根 README 的版本示例应与 `VERSION` 同步；
- 不得把“工作流已创建”写成“构建已通过”；
- 未实际执行的测试必须明确为未验证。

## 文档验证

在仓库根目录执行：

```bash
python scripts/release_baseline.py validate
```

在 `vitepress-doc` 目录执行：

```bash
npm ci
npm run docs:build
```

还应人工检查：

- 用户站点不包含内部资料；
- 侧边栏所有页面可打开；
- 搜索能找到新增页面；
- Mermaid、表格和代码块正常渲染；
- 移动端导航可用；
- 版本号与根 `VERSION` 一致。

## PR 检查清单

- [ ] 文档只描述已经进入本分支的代码；
- [ ] 新增功能有用户操作说明；
- [ ] 新配置有默认值、风险和生产建议；
- [ ] 新权限写明继承关系和后端边界；
- [ ] 数据迁移说明包含备份、校验和恢复；
- [ ] 没有真实患者数据和密钥；
- [ ] 导航和链接已更新；
- [ ] `npm run docs:build` 通过；
- [ ] 根 README、发布说明和变更日志没有互相矛盾。

## SVG 与截图维护约定

本轮采用静态 SVG 图解，使用统一视图框、标题、描述、阶段卡片和明确的风险提示。用户图放在 `user-guide/assets/`，内部图放在 `internal/assets/`，以相对路径引用；不要把内部拓扑、配置或诊断信息放进两个站点共享的 `public/` 目录。SVG 不使用脚本、远程字体、外链图片或真实患者数据。流程图必须标注为示意，不能冒充真实界面。

实际截图应使用隔离 Mock 或经过批准的脱敏数据，记录页面、主题、视口、提交身份及捕获日期。历史截图无法确认身份时明确标注，保留原始文件，不以示意图伪造实测结果。更新文档后验证用户与内部站点构建、链接及图片资源，不通过关闭死链检查规避错误。

### 图文交替与阅读层级

- 用户页面先给出任务入口和前置条件，再用实际操作步骤解释，不要求读者记忆数据库字段；技术词首次出现时同时解释它的业务含义。
- 图解放在相关操作之前或原理说明之间，而不是统一堆到页面末尾；图下使用一句图注说明重点及示意边界。
- 独立技术细节、接口路径、配置默认值与实现限制归入内部手册，不能让用户手册承担开发者文档的职责。
- 可查看原图的 SVG 使用页面内 `?url` 导入与真实构建资源链接，避免 Markdown 原图链接指向不存在的源目录；保持用户/内部资源隔离。
- 验收覆盖桌面、窄屏、键盘链接、实际 SVG 响应和构建死链检查。优先使用文字和结构解释，只有图能降低理解成本时才新增插图。


### 界面图解的事实来源

界面示意与逻辑流程图分别维护。本轮以候选提交 d248089d、经典浅色主题、隔离 Mock 1440×960 视口的实际浏览器矩形与组件标签为基线，重绘查询卡片、影像三栏、数据关系总览及运维总览上部。简化导航、文书和非关键细节，明确示意、主题、裁切范围和合成数据，不将示意图冒充软件截图。逻辑图保持职责和状态关系，不强行添加页面外壳。主题、控件或布局变更后，优先用 Mock 重新测量关键区域，而不是按印象更新 SVG。
