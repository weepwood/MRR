# OSS 迁移管理

OSS 迁移管理用于把现有图片源中的病案图片逐步上传到对象存储，并把 OSS Object Key、文件大小与 MD5 写回扫描记录。

当前系统采用“先检查、再试迁移、逐批扩大、最后全量”的方式。部署新版本后不会自动上传任何图片，也不会自动删除原始图片。

## 一、迁移前必须确认

进入 **系统管理 → OSS 迁移管理**，先查看“迁移前检查”。以下项目全部通过后，才允许创建任务：

- OSS 客户端已配置，能够生成签名 URL；
- 当前实际使用的图片来源可读取；
- 本地来源的 `image.base-path` 正确，或 NAS、Nginx、HTTP 来源节点配置正确；
- 运行后端服务的 Windows 账号对本地或 NAS 目录具有读取权限；
- 当前没有其他迁移任务；
- 抽样记录中至少存在可读取的真实文件。

迁移前检查会复用影像查看和导出功能使用的多来源解析链路，只读取配置、数据库和少量抽样文件，不会上传文件或更新迁移状态。

## 二、支持的图片来源

迁移任务支持项目现有的图片来源：

- 本地磁盘；
- NAS 或 Windows 共享目录；
- Nginx 静态资源；
- 受控 HTTP 图片源；
- `AUTO` 模式下按现有来源优先级解析的图片。

本地可读文件会直接上传。NAS、Nginx 或 HTTP 图片会通过现有 `ImageStorage` 读取到单个临时文件，上传结束后立即删除。应用异常退出遗留的迁移临时文件会在下次启动时清理；临时目录位于 Java 系统临时目录下的 `mrr-oss-migration`。

迁移日志只记录来源类型和 Scan ID，不记录带凭据的远程 URL。

## 三、首次迁移顺序

### 1. 选择真实目录

优先选择以下特征的目录：

- 图片数量在 100～500 张之间；
- 同时包含普通病案号和病案号大于等于 `10000000` 的记录；
- 同时覆盖目前真实使用的本地、NAS 或 Nginx 来源；
- 包含系统日常会查看和导出的真实病案；
- 原始图片完整且可访问。

### 2. 创建试迁移

选择“试迁移”，数量先填写 `100`，并限定到上一步选定的目录。

任务创建时会固定：

- 当前可迁移记录的最大 Scan ID；
- 本次计划处理数量；
- 可选目录范围。

后续新增的扫描图片不会混入正在运行的任务。

### 3. 核验结果

试迁移完成后，至少核对：

1. 迁移任务的计划数、处理数与失败数；
2. 影像档案袋可以正常打开 OSS 图片；
3. 同一病案中 OSS 与本地、NAS 或 Nginx 图片可以混合降级访问；
4. 下载 ZIP 和导出 PDF 的图片数量、顺序和内容正确；
5. OSS 中 Object Key 符合以下格式：

```text
medical-records/年月份/日期目录/目录键-病案号/文件名
```

病案号小于 `10000000` 时，目录键使用 `BRXH`；病案号大于等于 `10000000` 时，目录键使用唯一 `SJH`。

6. 数据库中的 `oss_url` 保存 Object Key，而不是临时签名 URL；
7. `file_size` 和 `checksum_md5` 已写入；
8. 审计日志没有出现异常的大量失败请求；
9. Java 临时目录没有持续累积迁移文件；
10. OSS 请求量、流量和存储费用符合预期。

## 四、扩大迁移批次

首次试迁移通过后，建议按以下级别逐步扩大：

| 阶段 | 建议数量 | 进入下一阶段的条件 |
| --- | ---: | --- |
| 试迁移 | 100～500 | 查看、下载、导出和日志全部正常 |
| 小批次 | 1,000 | 无对象冲突，失败原因可解释 |
| 中批次 | 10,000 | 连续批次稳定，服务器负载正常 |
| 大批次 | 50,000～100,000 | OSS 费用、网络和数据库写入均稳定 |
| 全量 | 当前快照全部 | 人工输入确认短语后启动 |

全量迁移必须输入：

```text
确认全量迁移
```

这只是防止误触，不代表可以跳过前面的试迁移和批次核验。

## 五、失败与重试

系统把失败分为两类：

### 永久失败

例如：

- 所有受控图片来源均不存在或不可读；
- `folder`、病案号、上架号或文件名无法构建安全路径；
- OSS 已存在同名对象，但 MD5 与原始图片不一致。

永久失败会退出待迁移集合，不会在同一任务中无限循环。处理源文件、来源节点或数据后，可在迁移日志中选择失败记录并执行“重置失败记录”，然后重新创建试迁移。

### 临时失败

例如图片源或 OSS 网络超时、连接中断、服务短暂不可用。系统使用有限次数的退避重试，最大尝试次数为 3 次。超过上限后转为永久失败，等待人工处理。

## 六、安全取消与应用重启

点击“安全取消”后，系统会等待当前图片处理结束，再停止领取新记录。已经迁移成功的图片不会回滚，尚未处理的图片保持待迁移状态。

如果迁移期间应用异常退出：

- 活动任务会标记为 `interrupted`；
- 遗留的 `migrating` 记录会恢复为可重试状态；
- 超过 24 小时的遗留迁移临时文件会在下次启动时清理；
- 重启后需要管理员重新执行迁移前检查并创建新任务。

## 七、何时应立即停止

出现以下任一情况，应安全取消当前任务并排查：

- 同名对象 MD5 冲突；
- 抽样或任务中大量源文件缺失；
- 影像档案袋访问 OSS 图片不稳定；
- ZIP/PDF 导出出现缺图、错序或反复使用旧结果；
- 后端内存、磁盘临时目录或数据库连接持续异常；
- OSS 请求量或费用明显超出预估；
- 迁移失败率连续两个批次超过 1%。

## 八、原始图片删除策略

本功能只负责复制和校验，不自动删除本地、NAS、Nginx 或 HTTP 来源的原始图片。

至少在以下条件全部满足前，不应清理原始图片：

- 全量迁移完成；
- 完成独立抽样校验；
- 影像查看和导出稳定运行一段时间；
- 已验证备份与恢复流程；
- 医院内部数据保留规范允许删除；
- 已形成可审计的删除清单和审批记录。
