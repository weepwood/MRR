# OSS 迁移管理

OSS 迁移管理用于把现有图片源中的病案图片逐步上传到对象存储，并把 OSS Object Key、文件大小与 MD5 写回扫描记录。

当前系统采用“先检查、再试迁移、逐批扩大、最后全量”的方式。部署新版本后不会自动上传任何图片，也不会自动删除原始图片。

## 一、迁移前必须确认

进入 **系统管理 → OSS 迁移管理**，先查看“迁移前检查”：

- OSS 客户端必须已配置，并且能够生成签名 URL；
- 当前不能存在其他活动迁移任务；
- Nginx 图片服务器地址、BA01/BA02/BA03 路由和可选 Basic Auth 必须配置正确；
- 后端必须能够通过 HTTP/HTTPS 访问 Nginx 图片服务；
- 抽样结果用于提示风险，不会因为少量缺图阻塞其他有效记录；
- 上架号为空、少于 4 位或包含非数字字符的记录不会上传，也不会计入失败。

迁移前检查只通过现有 Nginx 路由读取少量抽样图片，不会上传文件或回填 OSS 字段。

若全局抽样没有找到可读图片，系统仍允许创建限定目录的**试迁移**。此时必须先选择已经人工确认存在真实图片的目录，并保持 100～500 张的小规模范围。限定批次和全量迁移仍要求当前选择范围内至少存在可读来源。

## 二、正式迁移图片来源

OSS 迁移任务统一通过受控 Nginx 图片服务获取原图，不再优先读取后端本地磁盘，也不通过 NAS/HTTP 多来源链路决定迁移结果。

系统复用 `ImageUrlService` 的 BA01、BA02、BA03 路由规则，通过 HTTP GET 将单张图片写入 Java 临时目录 `mrr-oss-migration`。上传结束后立即删除；应用异常退出遗留超过 24 小时的临时文件会在下次启动时清理。

影像查看、ZIP/PDF 导出仍可保留 OSS、本地、Nginx 等多来源降级；这里的 Nginx 强制规则仅用于 OSS 正式迁移，以保证迁移源与浏览器实际看到的原图一致。

迁移日志只记录 `NGINX` 和 Scan ID，不保存带凭据的远程 URL。

## 三、首次迁移顺序

### 1. 选择真实目录

优先选择以下特征的目录：

- 图片数量在 100～500 张之间；
- 同时包含普通病案号和病案号大于等于 `10000000` 的记录；
- 同时覆盖目前真实使用的本地、NAS 或 Nginx 来源；
- 包含系统日常会查看和导出的真实病案；
- 原始图片完整且可访问。

### 2. 创建试迁移

选择“试迁移”，数量先填写 `100`，并限定到上一步选定的目录。

任务创建时会固定：

- 当前可迁移记录的最大 Scan ID；
- 本次请求的最大处理数量；
- 可选目录范围。

后续新增的扫描图片不会混入正在运行的任务。

试迁移和限定批次不会为了显示计划数而对三千万级数据执行一次全量精确计数；如果快照内实际可领取记录少于请求数量，任务完成时会把最终计划数收缩为实际处理数。只有人工确认的全量迁移会执行范围内精确计数。

### 3. 核验结果

试迁移完成后，至少核对：

1. 迁移任务的计划数、处理数与失败数；
2. 影像档案袋可以正常打开 OSS 图片；
3. 同一病案中 OSS 与本地、NAS 或 Nginx 图片可以混合降级访问；
4. 下载 ZIP 和导出 PDF 的图片数量、顺序和内容正确；
5. OSS 中 Object Key 符合以下格式：

```text
medical-records/上架号前4位/上架号-病案号/文件名
```

例如上架号 `00123456`、病案号 `00789124`、文件名 `0013.jpg`：

```text
medical-records/0012/00123456-00789124/0013.jpg
```

上架号始终按字符串处理并保留前导零，不再使用 `folder` 或 `BRXH` 参与 OSS Object Key。

6. 数据库中的 `oss_url` 保存 Object Key，而不是临时签名 URL；
7. `file_size` 和 `checksum_md5` 已写入；
8. 审计日志没有出现异常的大量失败请求；
9. Java 临时目录没有持续累积迁移文件；
10. OSS 请求量、流量和存储费用符合预期。

## 四、扩大迁移批次

首次试迁移通过后，建议按以下级别逐步扩大：

| 阶段 | 建议数量 | 进入下一阶段的条件 |
| --- | ---: | --- |
| 试迁移 | 100～500 | 查看、下载、导出和日志全部正常 |
| 小批次 | 1,000 | 无对象冲突，失败原因可解释 |
| 中批次 | 10,000 | 连续批次稳定，服务器负载正常 |
| 大批次 | 50,000～100,000 | OSS 费用、网络和数据库写入均稳定 |
| 全量 | 当前快照全部 | 人工输入确认短语后启动 |

全量迁移必须输入：

```text
确认全量迁移
```

这只是防止误触，不代表可以跳过前面的试迁移和批次核验。

## 五、失败与重试

系统先区分“等待上架号”和真正的迁移失败：

### 等待上架号

上架号为空、少于 4 位或包含非数字字符时，记录归入 `waiting_sjh`。系统保留 Nginx 原图，不上传 OSS、不增加迁移尝试次数、不设置重试时间，也不计入任务失败数。上架号补齐后，该记录会自动重新满足领取条件，无需全表回填或人工重置。

真正的迁移失败分为两类：

### 永久失败

例如：

- Nginx 返回 404，确认原图不存在；
- 病案号或文件名包含非法路径字符；
- OSS 已存在同名对象，但 MD5 与原始图片不一致。

Nginx 404 或非法路径会标记永久失败；Nginx 超时、连接中断、502/503/504 等临时故障进入等待重试。

永久失败会退出待迁移集合，不会在同一任务中无限循环。处理源文件、来源节点或数据后，可在迁移日志中选择失败记录并执行“重置失败记录”，然后重新创建试迁移。

### 临时失败

例如图片源或 OSS 网络超时、连接中断、服务短暂不可用。

临时失败会写入 `retry_wait` 和下一次允许重试时间。当前单机内网版本不会让一个长任务在后台等待数分钟，也不引入额外调度平台；到达重试时间后，由管理员创建下一次试迁移或限定批次任务继续领取。每次领取会增加尝试次数，最大尝试次数为 3 次，超过上限后转为永久失败并等待人工处理。

迁移日志中的临时失败状态为 `retry_wait`，与扫描记录状态保持一致，不再先写成 `failed`。

## 六、安全取消与应用重启

点击“安全取消”后，系统会等待当前图片处理结束，再停止领取新记录。已经迁移成功的图片不会回滚，尚未处理的图片保持待迁移状态。

任务进度只更新处理数、失败数和百分比，不会覆盖数据库中已经写入的 `cancelling` 与 `cancel_requested`，因此取消请求不会被工作线程的旧内存状态冲掉。

如果迁移期间应用异常退出：

- 活动任务会标记为 `interrupted`；
- 遗留的 `migrating` 记录会恢复为可重试状态；
- 超过 24 小时的遗留迁移临时文件会在下次启动时清理；
- 重启后需要管理员重新执行迁移前检查并创建新任务。

## 七、OSS 文件资源管理器

进入 **业务 → OSS 文件浏览**，可以用接近 Windows 文件资源管理器的方式查看已经上传到 OSS 的文件。

页面提供：

- Bucket、Endpoint、当前页目录数、文件数和文件大小；
- 返回、上一级、地址栏和面包屑导航；
- 图标视图与详细信息视图；
- 左侧当前目录树、中央文件列表和右侧文件详情；
- 当前页文件名筛选；
- 图片在线预览；
- 使用临时签名 URL 在新窗口打开文件；
- 文件大小、修改时间、存储类型、ETag 和完整 Object Key；
- 使用 OSS continuation token 的上一页、下一页浏览。

OSS 本身没有真实文件夹。系统通过 Object Key 的 `/` 分隔符，把以下路径展示成三层虚拟目录：

```text
medical-records/
└─ 0012/
   └─ 00123456-00789124/
      └─ 0013.jpg
```

浏览器只允许访问 `medical-records/` 前缀，每次最多读取 200 个对象，后端通过 `prefix + delimiter + continuationToken` 向 OSS 查询。页面显示的目录数、文件数和大小仅代表当前页，不代表整个 Bucket 的精确总量，因此不会为了展示页面扫描数千万个对象。

当前浏览器为只读模式，不提供：

- 删除文件；
- 移动或重命名文件；
- 修改 Object Key；
- 上传任意本地文件；
- 浏览 `medical-records/` 以外的对象。

这样可以防止管理员在查看生产病案影像时误删或移动对象。文件上传和失败重试仍统一从“OSS 迁移管理”页面执行。

## 八、何时应立即停止

出现以下任一情况，应安全取消当前任务并排查：

- 同名对象 MD5 冲突；
- 抽样或任务中大量源文件缺失；
- 影像档案袋访问 OSS 图片不稳定；
- ZIP/PDF 导出出现缺图、错序或反复使用旧结果；
- 后端内存、磁盘临时目录或数据库连接持续异常；
- OSS 请求量或费用明显超出预估；
- 迁移失败率连续两个批次超过 1%。

## 九、原始图片删除策略

本功能只负责复制和校验，不自动删除本地、NAS、Nginx 或 HTTP 来源的原始图片。

至少在以下条件全部满足前，不应清理原始图片：

- 全量迁移完成；
- 完成独立抽样校验；
- 影像查看和导出稳定运行一段时间；
- 已验证备份与恢复流程；
- 医院内部数据保留规范允许删除；
- 已形成可审计的删除清单和审批记录。
